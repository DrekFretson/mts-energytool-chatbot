# МТС EnergyTool: ИИ-консультант (MVP)

Консультант для сайта: выясняет задачу клиента, отвечает по базе знаний, показывает ссылки на страницы сайта, в подходящий момент предлагает менеджера и собирает заявку с резюме диалога. На сайт встраивается всплывающим виджетом одной строкой кода, ответ печатается по мере генерации. Одно ядро `core/` работает и в сабмите для LLM-судьи, и в веб-чате.

## Запуск

1. Положите архив базы знаний из материалов кейса (файл `knowledge-base.zip`) в `data/knowledge-base.zip`. В репозитории его нет: данные кейса публиковать нельзя. Без файла сервис остановится с сообщением, куда его положить. Если Docker уже успел создать на этом месте пустую папку `data/knowledge-base.zip`, удалите её.
2. Создайте `.env` (в нем `DEBUG_TOKEN` для отладки, `/admin` и `/manager`, и при желании подключение модели):

```bash
cp .env.example .env
```

3. Одна команда:

```bash
docker compose up --build
```

Страницы (порт на хосте меняется переменной `PORT`):

| Адрес | Что это |
|---|---|
| http://localhost:8000 | демонстрационная страница "как на сайте" со всплывающим виджетом чата |
| http://localhost:8000/chat | чат на всю страницу с режимом отладки |
| http://localhost:8000/admin | история всех диалогов и заявок (нужен `DEBUG_TOKEN`) |
| http://localhost:8000/manager | кабинет менеджера: очередь заявок, переписка с клиентом, отчет (нужен `DEBUG_TOKEN`) |

Заглушка `fake-llm` слушает 9000 только внутри сети compose.

## Подключение модели

Нужен OpenAI-совместимый сервер с `/chat/completions`; `/embeddings` и `/rerank` желательны.

| Что | Значение |
|---|---|
| Сервис | прокси организаторов или OpenRouter (`https://openrouter.ai/api/v1`) |
| Модель | `qwen/qwen3.8-27b` (по умолчанию), эмбеддинги `baai/bge-m3`, реранкер `qwen/qwen3-reranker-8b` |
| `LLM_BASE_URL` | адрес сервера, например `https://openrouter.ai/api/v1` |
| `LLM_MODEL` | идентификатор модели у этого сервера |
| `LLM_API_KEY` | ключ: выдают организаторы для своего прокси, для OpenRouter создается в личном кабинете openrouter.ai (раздел Keys) |

Значения пишутся в `.env`, ключ в репозиторий не попадает. Без `LLM_BASE_URL` веб ходит в `fake-llm`: интерфейс и заявка работают, но на каждый вопрос приходит текст-заглушка `[fake-llm] Ответ-заглушка...`. Если сервер не отдает `/rerank`, поиск работает без реранка, без `/embeddings` остается BM25, при сбое чата приходит запасной ответ.

## Проверка основного сценария

1. Открыть http://localhost:8000: чат уже открыт в правом нижнем углу (кнопка сворачивает и разворачивает его). Задать вопрос о задаче, например про снижение расходов на электроэнергию. Пока идет поиск и модель рассуждает, видно, что происходит ("Ищу в материалах", "Обдумываю ответ"), затем ответ печатается по мере генерации. Кнопка "Отмена" останавливает генерацию. Под ответом появляются ссылки на подходящие страницы сайта EnergyTool.
2. Задать уточняющий вопрос: консультант учитывает весь диалог.
3. Когда задача понятна и дальше нужен расчет, цена, КП или данные объекта, классификатор (маршрут `ready`) один раз предлагает связаться с менеджером. Если клиент сам просит менеджера (маршрут `operator`), форма заявки открывается сразу. Кнопка "Связаться с менеджером" в шапке доступна всегда. С `fake-llm` маршруты задаются меткой `[ready]` или `[operator]` в тексте вопроса.
4. Заполнить форму тестовыми данными и дать согласие: чат подтвердит, что заявка передана менеджеру вместе с резюме диалога.
5. Включить "Отладка" и ввести `DEBUG_TOKEN`: под ответами появятся время ответа по этапам (поиск, модель, время до первого слова) и документы базы знаний, вошедшие в ответ. При неверном токене чат об этом скажет и предложит ввести его снова.
6. Открыть `/manager`, ввести `DEBUG_TOKEN`: заявка стоит в очереди с резюме диалога. Менеджер принимает ее, пишет клиенту прямо в чат (бот в это время не отвечает, клиент видит, что сообщение передано менеджеру) и закрывает заявку отчетом. После закрытия снова отвечает бот.
7. Открыть `/admin`, ввести `DEBUG_TOKEN`: видны все сессии, в том числе без заявки, диалоги, заявка с резюме и отчет менеджера.
8. "Новый диалог" начинает новую сессию без контекста прошлой, старая остается в истории. Перезагрузка страницы диалог сохраняет, закрытие вкладки начинает его заново.

## Архитектура

```
core/       ядро и сабмит, плоские модули, только разрешенные пакеты
  kb.py         zip -> фрагменты с крошками, разбор pandoc-таблиц
  retrieval.py  bge-m3 + BM25, реранк с откатом; первыми в контекст идут разделы с ограничениями и со списком нужных от клиента сведений
  llm.py        чат, эмбеддинги, реранк, ретраи
  router.py     LLM-классификатор реплики: operator, ready, question
  prompts.py    правила консультанта, классификатор, резюме
  examples.py   банк утвержденных ответов: образцы стиля из демо-набора кейса, их можно дополнять
  pipeline.py   answer(index, history, note) -> {text, route, sources, timings, unverified_numbers}
  solution.py   точка входа платформы
  config.py     все параметры экспериментов
web/        FastAPI, SQLite
  app.py            сессии, поток ответа (SSE), заявка с резюме, история, кабинет менеджера
  stream.py         поток ответа по мере генерации поверх ядра: ядро и архив сабмита не меняются
  site_links.py     подбор ссылок на страницы сайта LLM-классификатором
  site_links.json   список страниц сайта: правится без изменения кода
  static/           widget.js (виджет для сайта), site.html (демо-страница), index.html (чат), admin.html, manager.html
eval/       поведенческие метрики ответа
tests/      автотесты и заглушка LLM
```

Веб на каждую реплику ищет фрагменты базы, генерирует ответ потоком и параллельно двумя короткими вызовами классифицирует реплику (маршрут к менеджеру и подходящие страницы сайта): задержку это не добавляет. Адреса страниц модель не видит и не пишет, их подставляет сервер из `site_links.json`. Диалоги, ответы с метаданными и заявки хранятся в SQLite (`DB_PATH`, в Docker том `app-data`). Сбой внешнего сервиса не роняет ответ: без реранкера остается гибрид, без эмбеддингов BM25, без LLM запасной текст. `submission.csv` создается сразу и переписывается атомарно, дедлайн 18 минут.

## Переменные окружения

| Переменная | Назначение |
|---|---|
| `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` | OpenAI-совместимый сервер, ключ и модель |
| `EMB_MODEL`, `RERANKER_MODEL` | Модели эмбеддингов и реранка |
| `LLM_PROVIDER` | Только для OpenRouter: фиксированный провайдер, например `deepinfra/bf16` |
| `EMB_BASE_URL`, `EMB_API_KEY` | Отдельный сервер эмбеддингов; по умолчанию `LLM_BASE_URL` и его ключ |
| `DEBUG_TOKEN` | Доступ к отладке, `/admin` и `/manager`; пустой значит отключено |
| `EMBED_ORIGINS` | Сайты, которым разрешено встраивать чат во фрейм, через пробел; по умолчанию `https://energytool.mts.ru` |
| `DB_PATH`, `KB_PATH` | SQLite и архив базы знаний |
| `PORT` | Порт на хосте, по умолчанию 8000 |
| `MESSAGES_PER_MINUTE` | Лимит сообщений с одного IP, по умолчанию 20 |
| `ANSWER_BUDGET_SEC` | Сколько ждать ответа модели, потом запасной текст (и при потоковом ответе), по умолчанию 90 |
| `WEB_ROUTER` | `parallel` (по умолчанию) или `off`: классификатор реплик в вебе |
| `DATA_DIR`, `MAX_WORKERS`, `MAX_TOKENS` | Передает платформа в сабмите |

## Зависимости

Docker с Compose v2. Без Docker: Python 3.13 и пакеты из `requirements.txt` с точными версиями (FastAPI, uvicorn, pydantic, httpx, numpy, rank-bm25).

## Разработка

```bash
python -m venv .venv && .venv/bin/pip install -r requirements.txt
```

```bash
.venv/bin/python -m unittest discover -s tests
```

Сабмит:

```bash
python build_zip.py
```

Архив появится в `dist/submission.zip`. Настройки по умолчанию в `core/config.py` - это вариант V9-wide, лучший результат на платформе (69.46; повтор того же архива дал 65.70, разброс судьи около 4 баллов): широкий контекст (найденный раздел тянет в контекст весь свой документ в пределах `CONTEXT_CHARS` = 60 тыс. символов, последние реплики диалога повторяются после материалов) и рассуждения модели (`REASONING_EFFORT = "xhigh"`). Бюджет ограничивает контекст при любом размере базы.

Точный вариант (62.1 на платформе: разделы, отобранные реранкером, 14 тыс. символов) собирается с параметрами, которые подменяют строки `config.py` внутри архива:

```bash
python build_zip.py V7-think 'WHOLE_DOCUMENTS=False' 'CONTEXT_CHARS=14000' 'DIALOG_RECAP=False'
```

Локальный прогон на демо-вопросах (нужен запущенный сервер LLM в `LLM_BASE_URL`):

```bash
DATA_DIR=data PYTHONPATH=core .venv/bin/python core/solution.py && .venv/bin/python eval/report.py submission.csv data/demo_output.csv
```

## Встраивание в сайт EnergyTool и передача заявок

Встраивание сделано виджетом. На страницу сайта добавляется одна строка:

```html
<script src="https://АДРЕС_СЕРВИСА/widget.js" defer></script>
```

Скрипт рисует кнопку в правом нижнем углу и по клику открывает панель с чатом во фрейме (`/chat?embed=1`); на телефоне панель занимает весь экран. Фрейм создается при первом открытии, поэтому страница сайта не ждет загрузки чата. Запросы чата идут на адрес сервиса, CORS не нужен. Встраивать чат разрешено только сайтам из `EMBED_ORIGINS` (заголовок `Content-Security-Policy: frame-ancestors`), остальные страницы сервиса во фрейм не встраиваются. Как это выглядит, показывает демонстрационная страница `/`.

Ссылки под ответом ведут на страницы сайта, а не на внутренние документы базы: клиент сразу попадает на страницу решения. Список страниц лежит в `web/site_links.json`, адреса в нем проверены по содержимому страниц 14.11.2026. Документы базы знаний, использованные в ответе, видны в режиме отладки.

Заявка сохраняется в таблице `leads` (ФИО, телефон, компания, время согласия, резюме диалога), диалог в `messages`. Менеджер работает в `/manager`: видит очередь заявок с резюме, принимает заявку, переписывается с клиентом в том же чате и закрывает ее отчетом; отчет виден в `/admin`. Данные доступны и через API: `/api/manager/queue`, `/api/admin/sessions`, `/api/admin/sessions/{id}`.

План, в коде этого нет:
- Отправка заявки с резюме в CRM (amoCRM, Bitrix24) или письмом в отдел продаж из `create_lead` (`web/app.py`); при сбое отправки заявка остается в `leads`, и ее можно отправить повторно.
- Отдельные учетные записи менеджеров вместо общего `DEBUG_TOKEN`.

## Известные ограничения

- Модель отвечает с рассуждениями: до первого слова ответа обычно 8-12 секунд, отдельные ответы до 50 секунд. Все это время чат показывает, что происходит, затем текст печатается по мере генерации. Если сервер модели не умеет отдавать ответ потоком, ответ приходит целиком.
- Ссылки на сайт и момент предложения менеджера определяют LLM-классификаторы, с `fake-llm` они срабатывают только по меткам (`[ready]`, `[operator]`, `[link:solar]`). Предложение менеджера показывается один раз за диалог и не показывается после заявки. Классификаторы видят последние 6 реплик: отказ от контактов раньше этого окна они не учтут.
- Модель видит последние 12 сообщений диалога; сообщения менеджера в них не входят.
- Заявка оформляется только через форму: контакты, написанные в чат, не сохраняются.
- Один `DEBUG_TOKEN` открывает отладку, `/admin` и `/manager`: для промышленной работы нужны отдельные учетные записи.
- SQLite и лимиты запросов рассчитаны на один экземпляр сервиса; за обратным прокси все клиенты делят один лимит по IP.
- База знаний при каждом запуске заново индексируется через `/embeddings`.
